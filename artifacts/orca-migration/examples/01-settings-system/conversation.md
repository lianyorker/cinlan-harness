### 决策 1：配置文件格式

**问题**：是否保留 Orca 的 JSON 格式，还是改用 YAML/TOML？

**讨论**：
- 选项 A：保留 JSON（兼容性好）
- 选项 B：改用 YAML（更易读）

**最终决定**：选项 A

**理由**：
- 与 Orca 完全兼容
- JSON 解析库成熟稳定
- 未来可以通过适配器支持其他格式

**理由**：
- 确保行为一致
- 避免引入新的边界情况

## 收获和教训

### 收获 1：理解了 Orca 的配置系统设计哲学

Orca 的配置系统设计非常简洁，所有配置都是平铺的 JSON 对象，没有深层嵌套。这种设计：
- 易于理解和修改
- 减少了配置合并的复杂度
- 但牺牲了配置的结构化

Harness 可以保留这种简洁性，但在内部实现时可以使用类型化的配置对象。

---

### 收获 2：行为对比测试的重要性

在编写单元测试时，我以为已经覆盖了所有情况，但行为对比测试发现了 3 个边界情况的不一致：
- 空配置文件
- 只有注释的配置文件（JSON 不支持注释，但 Orca 可能用了 JSON5）
- 超大配置文件（10MB+）

这些都是单元测试没有覆盖到的。

---

### 教训 1：不要跳过分析直接写代码

一开始我想直接写代码，但发现对 Orca 的理解不够深入，写出来的代码与 Orca 行为不一致。后来花时间仔细分析 Orca 的代码后，实现就顺利多了。

**建议**：花 30% 时间分析，20% 时间设计，50% 时间实现和测试。

---

### 教训 2：及时记录决策和理由

有些决策当时觉得很显然，但一周后回头看就忘了为什么这样做。建议每做一个重要决策，立即在对话中或笔记中记录下来。
