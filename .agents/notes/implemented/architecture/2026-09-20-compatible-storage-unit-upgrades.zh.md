# Agent Note: 显式兼容存储单元升级

Status: implemented

[English](2026-09-20-compatible-storage-unit-upgrades.md) | 中文

## 问题

领域可以增加可选字段，同时保持当前 schema 对存储前代记录的接受能力。拒绝所有旧整单元版本戳，会阻止该领域跨单调版本增长打开数据。打开时推进版本戳会使单纯检查变成写入，而把版本戳与数据写入分开提交，则可能宣称一个数据操作实际失败的升级。

## 决策

领域所有者通过 `compatibleVersions` 声明兼容前代。条目必须是明确列出且小于当前版本的非负整数，当前记录与全局值 schema 必须接受其值。整单元 JSON 与 SQLite 接纳当前版本戳或列出的旧版本戳；未列出的旧版本和未来版本被拒绝。这是 schema 兼容准入，不是记录转换，也不允许降低当前版本。

兼容整单元的打开与 `loadAll()` 保留存储值及现有版本戳。JSON 以当前版本构建内存状态，在下一次成功的原子文件替换时共同发布该版本戳。发布失败保留前代文件；删除不存在的 JSON 键不执行发布。

SQLite 对 `putRecord`、`deleteRecord` 和 `setGlobal` 使用 `BEGIN IMMEDIATE`。它在事务内重新检查存储版本戳，执行数据操作，更新 `units.version`，然后提交。失败同时回滚数据和版本戳。其他句柄提交较新版本后，以旧版本打开的句柄不能再写入。兼容单元升级不改变物理 DDL；`STORAGE_SQLITE_SCHEMA_VERSION` 及其精确版本数据库准入与领域所有者声明的单元版本分开。

[投影缓存兼容决策](2026-09-02-projcache-cross-version-read-compat.zh.md)继续负责逐记录准入、旧文件初始化、语义身份检查和 backup-and-skip。本决策扩展整单元后端准入，不改变这些机制。[已发布 Session JSONL 代次](2026-08-31-released-session-format-migrations.zh.md)保留独立的相邻迁移规则。

## 备选方案

**整单元读取要求精确版本。** 即使所有者能够使用当前 schema 验证每个存储值，这仍会拒绝结构兼容的前代数据。

**打开时重写版本戳。** 打开或检查数据会变成升级操作，随后被拒绝的写入则会留下已推进但不含预期变化的版本戳。

**独立提交 SQLite 版本戳。** 分开提交可能在失败后留下不一致的数据和版本。事务前的版本检查也会允许旧打开句柄覆盖已经提交的升级。

**接受所有更低版本。** 版本先后关系本身不能证明 schema 或语义兼容性；只有领域所有者可以指定可接受的前代。

## 影响

所有者必须保持当前版本单调，并明确论证每个兼容前代。不兼容的 schema 变化仍需所有者定义的转换。成功写入当前版本后，曾读取前代并不代表支持降级。JSON 保留调用方负责的写入顺序，不会因兼容准入获得跨进程协调能力。

验证覆盖两个后端：读取已接受前代时保留存储版本戳，首次成功写入发布当前版本，拒绝未列出及未来版本，写入失败保留旧数据和版本戳，并由 SQLite 拒绝旧写入者降级尝试。逐记录兼容性和无效记录恢复保留原有测试。操作语义归属[存储参考](../../../../docs/subsystems/storage.zh.md)和各后端 README。
