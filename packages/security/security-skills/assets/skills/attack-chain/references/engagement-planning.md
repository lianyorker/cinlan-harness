# 渗透任务分解与委派规划

> 多阶段渗透任务如何拆成可执行子任务、何时委派、何时转向。适用于 attack-chain 编排和任何需要把大目标拆成子任务序列的场景。

---

## 子任务配比（10/30/30/30）

生成执行计划时按此结构分配子任务数量与耗时：

| 阶段 | 占比 | 内容 |
| --- | --- | --- |
| 环境侦察与事实收集 | ~10% | 确认目标可达性、工具可用性、已有凭据/材料就位 |
| 多路径实验 | ~30% | 并行设计多个候选攻击路径的探索性子任务，允许试错 |
| 评估选路 | ~30% | 显式评估各路径结果，选出最有希望的一条；包含决策点和转向条件 |
| 集中执行 | ~30% | 沿选定路径推进，每步有可度量的进展和验证点 |

要点：研究类子任务尽量前置，为后续步骤提供输入；优先直接行动而非过度准备；每个阶段建立在前一阶段之上并保持向目标收敛。

## 子任务编写要求

每个子任务 MUST：

- 有直接贡献于用户原始目标的明确标题和详细说明
- 描述**目标与产出**而非规定具体实现步骤（给执行者留方法弹性）
- 说明"为什么"——该子任务如何推进总目标
- 带有清晰的成功判据
- 可在单次执行会话内完成
- 不包含 GUI 应用、交互式终端会话、需要宿主机访问的操作

## 委派规则

- **先独立解决**：只有专家明显更快/更好时才委派，默认自己干
- **完整上下文**：每次委派 MUST 附带背景、当前目标、已收集发现、期望输出格式、成功判据、约束条件
- **批判性吸收**：对委派返回的结果做批判性评估后再整合进工作流，不照单全收
- **最小步数**：用最少委派次数完成子任务，避免为委派而拆分

## 执行边界与转向

- 只在当前子任务范围内工作；禁止提前执行计划中的后续子任务
- 同一方法失败 3 次后 MUST 切换到完全不同的策略，而不是微调重试
- 阴性结果也是有效产出——确认"此路不通"要如实记录并报告
- 每个子任务结束后，剩余计划允许被修订：新增发现的子任务、删除过时项、调整顺序（仅限未开始的项）

## 计划修订（执行中动态调整）

每个子任务完成后，对剩余计划做增量修订而不是整体重排：

- **操作类型**：add（插入新子任务）/ remove（删除过时项）/ modify（更新描述）/ reorder（调整顺序）——只提交变化部分
- **合并收缩**：删除已被前序结果覆盖的子任务，合并可一起执行的相关项，持续减少剩余总数
- **补洞**：为新发现的障碍或捷径新增子任务；为部分失败创建恢复路径
- **完成检测**：原始目标已达成或剩余项均无必要 → 清空计划即完成；遇不可逾越障碍同样清空并说明原因

### 失败分类与转向

| 失败类型 | 特征 | 处理 |
| --- | --- | --- |
| 技术性 | 命令/工具/参数问题 | 调整后重试 |
| 环境性 | 缺依赖/配置 | 修环境或换等价工具 |
| 概念性 | 方法本身错误 | 换完全不同的路径 |
| 外部性 | 系统控制外的限制 | 承认限制，改目标或如实记录 |

同一思路失败 2 次后 MUST 换根本不同的方案，禁止微调重试。

## 卡死自检（执行监控 6 问）

进展停滞时依次自问：

1. 我在向子任务目标产出可度量的进展，还是空转？
2. 是否在重复相同动作而没有新结果？
3. 是否陷入循环或方向错误？
4. 是否应该换完全不同的策略？具体换什么？
5. 当前子任务是否按其定义就不可能完成？应报告已完成部分并终止，还是需要更多信息？
6. 现在最关键、最可执行的下一步是什么？

## 升级通道（卡住时）

执行中遇到以下情况 SHOULD 主动请求上级/顾问指导，而不是继续空转：

- 同一目标反复失败且已换过策略
- 需要超出当前角色能力的领域知识（如渗透者需要 exploit 开发）
- 发现当前子任务本身定义有误或已过时

请求指导时提供：具体问题 + 已尝试的方法与输出 + 相关代码/命令片段。
